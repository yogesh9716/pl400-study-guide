What Is PL-400?

PL-400 is Microsoft's certification for Power Platform Developers — people who extend Power Platform beyond what makers can do: writing C# plugins, building PCF controls in TypeScript, creating custom connectors, integrating with Azure and Graph API, and managing ALM pipelines. It sits at the Associate level but its technical depth makes it genuinely hard.

As a SharePoint + Power Platform developer, you already know the ecosystem. Your gaps are likely in Dataverse plugin development, PCF component architecture, and ALM / CI-CD pipelines. This book covers everything — but pay extra attention to those three areas.

Chapter 01

Creating a Technical Design

Choosing the right tool, justifying the choice, identifying constraints

PL-400 doesn't just test code — it tests your ability to think like an architect. Given a business scenario, you must choose the correct technology, justify it, and identify trade-offs. This chapter gives you the decision framework.

Dataverse vs SharePoint: The Master Decision Matrix

CriteriaChoose DataverseChoose SharePoint Lists
Data volumeMillions of rows, complex queriesUnder ~5,000 rows per view (delegation limits)
RelationshipsComplex 1:N, N:N, rollup columns, lookupsSimple lookup columns
Business logicServer-side plugins, workflows, calculated columnsSimple validation rules or Power Automate
Row-level securitySecurity roles + Business Units + Field Security ProfilesSharePoint item-level permissions (limited)
Offline accessYes — model-driven apps with offline profilesLimited (SharePoint mobile app)
Reporting / dashboardsNative Power BI, Dataverse views, charts, dashboardsRequires external connection
CostPer-user or per-app premium license requiredIncluded in M365 license
Audit trailNative field-level auditingSharePoint version history (item level only)
Document storageSharePoint integration for file columnsNative document library
🎯 EXAM TRAP — The Most Common Wrong Answer When a scenario says "millions of records with row-level security and complex reporting" — the answer is Dataverse. When it says "document collaboration" or "M365 is already licensed and data is under 5,000 items" — the answer tips toward SharePoint. Cost is a legitimate factor in exam scenarios.
SharePoint Lists = a spreadsheet pinned to a wall. Great for simple team data, easily visible, no setup cost. Dataverse = a proper relational database with a security guard at every row and field. You don't bring a database where a spreadsheet works — but you don't run a hospital patient system on a spreadsheet either.

The Four-Layer Dataverse Security Model

Dataverse security is layered. A user must pass all applicable layers to access data. Each layer narrows access further.

LayerConceptConfigured InGranularity
1. Azure ADUser must have an Entra ID account and be licensed for Power PlatformAzure Portal / Microsoft 365 AdminEnvironment access
2. Security RolesCRUD + Append + Share privileges per table, per depthPower Platform Admin Center or SettingsTable + operation level
3. Business UnitsOrganizational hierarchy — scopes which records a user can see based on ownershipPower Platform Admin CenterRecord ownership depth
4. Field Security ProfilesColumn-level masking and restriction (must be enabled on the column first)Settings → Field Security ProfilesColumn level

Security Role Privilege Depths — The Core Concept

Every privilege in a security role has a depth. This is what the exam tests most frequently — not whether a user has permission, but HOW MUCH of the data they can access.

Depth SettingWhat the User Can AccessTypical Use Case
User (Self)Only records they personally ownField sales rep — sees only their own leads
Business UnitAll records owned by anyone in their Business UnitTeam manager — sees entire team's records
Parent: Child Business UnitTheir BU + all child BUs in the hierarchy below themRegional manager — sees all regional teams
OrganizationAll records in the environment, regardless of ownerSystem administrator or global reporting role
🎯 EXAM — Teams and Record Ownership Records can be owned by a User or a Team. When a record is owned by a Team, all team members with the appropriate security role depth can access it through the BU depth. If you need multiple people to share "ownership" of records without a BU hierarchy change, use an Owner Team.
⚠️ System Administrators Bypass Field Security The System Administrator role bypasses Field Security Profiles. If you need to hide a column even from system administrators, that is architecturally not possible with field security — you need a different data model (separate table, or application-layer enforcement).

Licensing questions on PL-400 follow a "which license does this scenario require?" pattern. These are the lines that matter:

If a flow uses any premium connector, every user who triggers it needs a premium license — OR the flow itself needs a per-flow license.

🧠 Chapter 1 Quiz

Q: A company needs to store 2 million customer records with row-level security based on the salesperson who owns each record, plus managers must see their entire team's records. Which data store is most appropriate?
Correct: B. SharePoint has a 5,000-item view threshold and cannot natively do row-level security based on organizational hierarchy. Azure SQL is valid but adds cost and complexity when Dataverse provides BU-based security natively. Dataverse + Security Roles + Business Units is exactly what this scenario describes.
Chapter 02

Dataverse Deep Dive

Tables, relationships, plugins, and the Web API — the engine of Power Platform

Dataverse is not just a database — it's a relational engine with built-in security, metadata-driven APIs, auditing, business logic execution, and event pipelines. Understanding its internals is what separates a Power Platform developer from a Power Platform user.

Table Types and Column Types

Table TypeDescriptionKey Trait to Remember
StandardRegular data table with rows, columns, relationshipsHas an Owner field by default (User or Team ownership)
ActivitySpecial time-stamped event table (Email, Task, Phone Call)Inherits from ActivityPointer; shows in activity timeline on forms
VirtualTable backed by external data source — data NOT stored in DataverseRead-only by default; requires data provider; cannot have FK relationships
ElasticHigh-scale table backed by Azure Cosmos DBEventual consistency; no traditional relationships; good for IoT/telemetry
🎯 EXAM TRAP — Virtual Tables Virtual tables do NOT store data in Dataverse. Data remains in the external system. They appear to Power Apps makers like regular tables, but queries go to the external provider at query time. You cannot create lookup relationships from virtual tables to standard Dataverse tables (no FK enforcement exists).

Column Types That Appear on the Exam

Column TypeDescriptionKey Exam Note
LookupForeign key to another table (creates N:1 relationship)Stores the related record's GUID; creates relationship automatically
Choice (Option Set)Dropdown of predefined valuesGlobal choices can be reused across multiple tables; Local choices cannot
FormulaCalculated at query time using Power Fx (same record's columns)Read-only; cannot be used in plugin Pre-Validation; not stored in DB
RollupAggregates data from related child records (Sum, Count, Min, Max, Avg)Updates every hour or on-demand — NOT real-time
Auto NumberGenerates sequential or pattern-based IDs (e.g., CASE-0001)Cannot be edited after record creation
File / ImageStores binary content directly in DataverseFile column max size is configurable up to 128 MB
Polymorphic LookupA lookup that can point to multiple table typesThe "Customer" field on Contact (Account OR Contact)
⚠️ Rollup vs Formula Column — They Are Very Different A Rollup column aggregates from related records across tables (e.g., total revenue from all Opportunities on an Account). A Formula column computes from other columns on the same record only (e.g., full name = first + last). They are frequently confused in exam scenarios.

Relationship Types

TypeExampleHow to CreateKey Behavior
1:N (One-to-Many)Account → many ContactsAdd Lookup column to child tableCascade behaviors (Delete, Share, Assign, Reparent)
N:1Contact → one AccountSame relationship, child's perspectiveSame relationship, different viewpoint
N:N (Native)Cases ↔ Knowledge ArticlesUse N:N relationship builderCreates system-managed intersect table (no custom columns)
N:N (Manual / Junction)Contacts ↔ Projects with Role attributeCreate table with two Lookup columnsCan store attributes ON the relationship itself
🎯 KEY — Native N:N vs Manual Junction Table If you need to store attributes on the relationship itself (e.g., "the role a Contact plays on a Project, and when they started") — you MUST use a manual junction table with two lookup columns. Native N:N creates a system-managed intersect table with no custom columns. This distinction appears on multiple PL-400 questions.

Plugin Development in C#

Plugins are server-side C# assemblies that execute within the Dataverse event pipeline. They are synchronous with the database transaction (when run in Stage 20 or Stage 40 sync), can cancel operations, modify data mid-flight, and call external APIs. If you know SharePoint event receivers, think of plugins as the same concept — but with richer context, better security, and a proper retry model.

The Plugin Execution Pipeline

Stage#TimingIn Transaction?Can Cancel?Async Available?
Pre-Validation10Before security check and before DB transaction❌ No✅ Yes❌ No
Pre-Operation20After security check, within transaction, before DB write✅ Yes✅ Yes❌ No
Main Operation30Platform writes to the DB✅ YesNot a plugin stageN/A
Post-Operation40After DB write, within transaction (sync) or after commit (async)✅ (sync) / ❌ (async)✅ (sync only)✅ Yes
⚠️ Stage 10 vs Stage 20 — Critical Difference Pre-Validation (Stage 10) runs outside the database transaction. Any Dataverse writes you perform inside it will NOT be rolled back if the main operation fails. Use Stage 20 (Pre-Operation) when your logic must be atomic with the main operation. Use Stage 10 only for lightweight validation that doesn't write data.

Plugin Code — The Full Production Pattern

C# — Complete IPlugin Implementation 
using Microsoft.Xrm.Sdk;
using Microsoft.Xrm.Sdk.Query;
using System;

namespace Contoso.Plugins
{
    public class ValidateAccountPlugin : IPlugin
    {
        private readonly string _unsecureConfig; // visible to customizers
        private readonly string _secureConfig;   // encrypted in DB

        // Constructor MUST match this signature for config injection from PRT
        public ValidateAccountPlugin(string unsecureConfig, string secureConfig)
        {
            _unsecureConfig = unsecureConfig ?? "https://api.example.com";
            _secureConfig = secureConfig; // e.g. API key, password
        }

        public void Execute(IServiceProvider serviceProvider)
        {
            // Step 1: Get execution context
            var context = (IPluginExecutionContext)serviceProvider
                .GetService(typeof(IPluginExecutionContext));

            // Step 2: Get tracing service — your ONLY debug output in production
            var tracer = (ITracingService)serviceProvider
                .GetService(typeof(ITracingService));

            // Step 3: Get org service factory
            var factory = (IOrganizationServiceFactory)serviceProvider
                .GetService(typeof(IOrganizationServiceFactory));

            // Create service as the triggering user (context.UserId)
            var service = factory.CreateOrganizationService(context.UserId);

            try
            {
                if (context.MessageName != "Create" && context.MessageName != "Update") return;

                // InputParameters["Target"] = the entity being created/updated
                if (!context.InputParameters.Contains("Target")) return;
                var target = context.InputParameters["Target"] as Entity;
                if (target?.LogicalName != "account") return;

                tracer.Trace($"Plugin fired: {context.MessageName} on Account {target.Id}");

                // Validate revenue — cancel if negative
                if (target.Contains("revenue"))
                {
                    var revenue = target.GetAttributeValue<Money>("revenue")?.Value ?? 0;
                    if (revenue < 0)
                        throw new InvalidPluginExecutionException(
                            "Revenue cannot be negative.");
                }

                // Enrich a computed field in Pre-Operation (Stage 20)
                if (target.Contains("name"))
                    target["con_nameslug"] = target
                        .GetAttributeValue<string>("name")?
                        .ToLower().Replace(" ", "-");
            }
            catch (InvalidPluginExecutionException) { throw; }
            catch (Exception ex)
            {
                tracer.Trace($"Error: {ex.Message}");
                throw new InvalidPluginExecutionException($"Plugin failed: {ex.Message}", ex);
            }
        }
    }
}
✅ Plugin Best Practices 1. Always trace with ITracingService — it's your only debug tool in production (enable under Settings → System Settings → Customization → Enable Plugin Trace Log).
2. Never hardcode credentials — use the Secure Config string from the Plugin Registration Tool.
3. Always catch and re-throw as InvalidPluginExecutionException — raw exceptions show unfriendly messages.
4. Plugins are stateless — don't store state in instance fields (plugin instances may be cached and reused).
5. Keep sync plugins fast — user waits for them. External HTTP calls in sync plugins are a UX risk.

Pre-Image and Post-Image

When a plugin fires on Update, the Target entity in InputParameters contains only the fields being changed in this operation — not all fields on the record. To read the full current state of the record, you need a Pre-Image registered in the Plugin Registration Tool.

C# — Using Pre-Image to Read Current Values Before Update 
// In PRT: on the plugin step, add Pre-Image → name it "PreImage"
if (context.PreEntityImages.Contains("PreImage"))
{
    var preImage = context.PreEntityImages["PreImage"];

    // Read OLD value (before update)
    var oldStatus = preImage.GetAttributeValue<OptionSetValue>("statuscode")?.Value;

    // Read NEW value from Target (what user is setting now)
    var newStatus = target.Contains("statuscode")
        ? target.GetAttributeValue<OptionSetValue>("statuscode")?.Value
        : oldStatus; // not being updated → same as old

    tracer.Trace($"Status: {oldStatus} → {newStatus}");
}
🎯 EXAM — Pre/Post Image Availability Rules Pre-Image: only available on Update and Delete messages.
Post-Image: only available on Create and Update in Stage 40 (Post-Operation).
A Pre-Image on Create makes no sense — there's no state before a creation.
Post-Images on Delete make no sense — the record is gone. Know these rules cold.

🧠 Chapter 2 Quiz

Q: A plugin on Account Update (Stage 20, Synchronous) reads the "Category" field via target.Contains("industrycode") and it sometimes returns false even though the Category field has a value on the record. What is the cause?
Correct: B. On an Update, Target contains only fields included in the update payload — not the full record. To read fields not being updated, register a Pre-Image on the plugin step in the Plugin Registration Tool. The Pre-Image is a snapshot of the full record before the update fires.

Canvas Apps — Delegation

Delegation is the most important canvas app concept for PL-400. When a function is delegable, Power Apps sends the filtering/sorting work to the data source (server-side). When it is NOT delegable, Power Apps downloads only the first 500 records (configurable to 2,000) and processes them in the browser — silently returning incomplete results for large datasets.

🎯 EXAM — The Blue Delegation Warning Power Apps Studio shows a blue underline / warning triangle when a formula contains a non-delegable function. This is a signal the exam uses in scenario questions: "users are not seeing all records" = delegation problem.

Essential Power Fx Patterns

Power Fx — Must-Know Patterns for PL-400 
// Patch: create or update a record
Patch(
    Accounts,
    Defaults(Accounts),          // Defaults() = new record; LookUp() = update existing
    {
        Name: TextInput_Name.Text,
        Revenue: Value(TextInput_Revenue.Text),
        'Account Category': 'Account Category'.Preferred
    }
)

// ForAll: bulk update multiple records
ForAll(
    colSelectedItems,
    Patch(Accounts, LookUp(Accounts, ID = ThisRecord.ID), {Status: "Reviewed"})
)

// IsBlank vs IsEmpty — EXAM TRAP
IsBlank("")                 // TRUE  — blank string is blank
IsBlank(null)              // TRUE  — null is blank
IsEmpty("")               // FALSE — IsEmpty is for tables/collections only
IsEmpty(colMyCollection)  // TRUE if collection has zero rows

// Coalesce: return first non-blank value
Coalesce(TextInput1.Text, TextInput2.Text, "Default")

// With: compute once, reuse (avoids repeated lookups)
With(
    {acc: LookUp(Accounts, Name = "Contoso")},
    acc.Revenue > 1000000 && acc.NumberOfEmployees > 50
)
🎯 EXAM — IsBlank vs IsEmpty IsEmpty("") returns FALSE. IsEmpty only checks if a table or collection has zero records. IsBlank("") returns TRUE. If an exam question asks how to check if a text field is empty, the answer is IsBlank(), not IsEmpty().

PowerApps Component Framework (PCF)

PCF controls are TypeScript/React components that replace the standard field or subgrid UI in Power Apps with custom rendering while staying fully integrated with the platform security and event model.

Field vs Dataset Controls

Field Control
  • Replaces a single field/column UI
  • Receives one value; can output one value
  • Example: star rating, color picker, barcode scanner
  • Manifest: <property> elements
Dataset Control
  • Replaces a view or subgrid
  • Receives multiple records; can filter, sort, page
  • Example: Kanban board, calendar, custom data grid
  • Manifest: <data-set> element

PCF Lifecycle — Four Key Methods

TypeScript — PCF Control Interface 
export class StarRatingControl
    implements ComponentFramework.StandardControl<IInputs, IOutputs>
{
    private _value: number;
    private _notifyOutputChanged: () => void;
    private _container: HTMLDivElement;

    // Called ONCE when control first loads
    public init(
        context: ComponentFramework.Context<IInputs>,
        notifyOutputChanged: () => void,
        state: ComponentFramework.Dictionary,
        container: HTMLDivElement
    ): void {
        this._notifyOutputChanged = notifyOutputChanged;
        this._container = container;
        this._value = context.parameters.ratingValue.raw ?? 0;
        this.render();
    }

    // Called when bound field value or form context changes
    public updateView(context: ComponentFramework.Context<IInputs>): void {
        this._value = context.parameters.ratingValue.raw ?? 0;
        this.render(); // re-render with new value
    }

    // Platform calls this AFTER notifyOutputChanged() to read new value
    public getOutputs(): IOutputs {
        return { ratingValue: this._value };
    }

    // Called when control is removed — clean up event listeners, timers
    public destroy(): void { }

    private render(): void {
        this._container.innerHTML = "";
        for (let i = 1; i <= 5; i++) {
            const star = document.createElement("span");
            star.textContent = i <= this._value ? "★" : "☆";
            star.style.cursor = "pointer"; star.style.fontSize = "24px";
            star.addEventListener("click", () => {
                this._value = i;
                this.render();
                this._notifyOutputChanged(); // Signal to platform: value changed
            });
            this._container.appendChild(star);
        }
    }
}
🎯 EXAM — PCF Lifecycle Order init() → updateView() (on every change) → getOutputs() (after notifyOutputChanged) → destroy() (on unload). The platform calls getOutputs() asynchronously after you call notifyOutputChanged() — they are not synchronous. Never call notifyOutputChanged() inside updateView() — that creates an infinite loop.

🧠 Chapter 3 Quiz

Q: A canvas app connected to SharePoint (50,000 records) has a gallery filtering by Status = "Active" AND Region = TextInput.Text. Users report incomplete results. What is the correct diagnosis and fix?
Correct: B. SharePoint delegation has limitations with complex multi-condition filters. With 50,000 records, only the first 500 (default limit) are retrieved and filtered locally. ClearCollect with 50,000 records is a performance disaster. The delegation limit max is 2,000 — not a real fix. Dataverse has much stronger delegation support.

⚠️ formatDateTime Case Sensitivity — Classic Exam Trap In Power Automate date format strings: MM = months (capital M), mm = minutes (lowercase m), dd = day, yyyy = 4-digit year. Writing "DD/MM/YYYY" (all uppercase) is wrong — DD and YYYY are not valid tokens. The correct format for 25/01/2026 is 'dd/MM/yyyy'.

Error Handling — Try/Catch Pattern

Power Automate doesn't have native try/catch, but you simulate it with Scopes and the "Run After" configuration.

🎯 EXAM — The Try/Catch Scope Pattern 1. Add a Scope action — name it "Try" — put your main logic inside
2. Add another Scope action — name it "Catch" — AFTER the Try scope
3. On the Catch scope: click ••• → Configure Run After → check "has failed" and "has timed out" (uncheck "succeeded" and "skipped")
4. Inside Catch: add error notification, log the failure, terminate with failure
This is the ONLY built-in error handling pattern in Power Automate and appears on multiple PL-400 questions.

The Xrm Object Model

The Xrm object model is the JavaScript API for interacting with model-driven app forms and views. It is the only supported way to write form scripts. Direct DOM manipulation is unsupported and will break in future updates.

⚠️ NEVER USE Xrm.Page — It Is Removed Xrm.Page was deprecated and is removed in Unified Interface. Any code using it will fail. Always use executionContext.getFormContext(). If you see Xrm.Page as an answer option on the exam, it is almost certainly wrong. This is the single most tested "deprecated API" question on PL-400.

The Correct Pattern — Always Start Here

JavaScript — Production-Ready Form Script Pattern 
"use strict";

// Namespace pattern prevents global variable conflicts
var Contoso = Contoso || {};
Contoso.AccountForm = (function () {

    // OnLoad: receives executionContext because checkbox is checked in form designer
    function onLoad(executionContext) {
        const formContext = executionContext.getFormContext(); // correct way

        // Register onChange on a field
        formContext.getAttribute("revenue").addOnChange(onRevenueChange);

        // Set required level
        formContext.getAttribute("description").setRequiredLevel("required");
        // Options: "none" | "recommended" | "required"

        // Show/hide a control
        formContext.getControl("con_customfield").setVisible(false);
    }

    function onRevenueChange(executionContext) {
        const formContext = executionContext.getFormContext();
        const revenue = formContext.getAttribute("revenue").getValue();

        if (revenue !== null && revenue > 1000000) {
            // Show a notification banner on the form
            formContext.ui.setFormNotification(
                "Large account: VP approval required.",
                "INFO",         // "ERROR" | "WARNING" | "INFO"
                "revenueInfo"  // unique key to clear it later
            );
        } else {
            formContext.ui.clearFormNotification("revenueInfo");
        }
    }

    // OnSave: can cancel the save using preventDefault
    function onSave(executionContext) {
        const formContext = executionContext.getFormContext();
        const phone = formContext.getAttribute("telephone1").getValue();

        if (!phone) {
            // Cancel the save
            executionContext.getEventArgs().preventDefault();
            // Show error on the field control (not on the attribute)
            formContext.getControl("telephone1").setNotification(
                "Phone number is required.", "phoneErr"
            );
        }
    }

    // Expose only public functions
    return { onLoad: onLoad, onSave: onSave };
}());
// Register as: Contoso.AccountForm.onLoad

public class ExternalApiPlugin : IPlugin
{
    private readonly string _apiEndpoint;
    private readonly string _apiKey;

    // Exact constructor signature required — no optional parameters
    public ExternalApiPlugin(string unsecureConfig, string secureConfig)
    {
        // Unsecure: visible to anyone with customization access
        _apiEndpoint = unsecureConfig ?? "https://api.example.com/v1";

        // Secure: encrypted — use for API keys, passwords
        if (string.IsNullOrEmpty(secureConfig))
            throw new InvalidPluginExecutionException(
                "Secure config (API key) not configured. Contact your administrator.");
        _apiKey = secureConfig;
    }

    public void Execute(IServiceProvider serviceProvider) { /* use _apiKey here */ }
}

Azure Integration Patterns

Azure Service Bus
  • Reliable message queuing

  • Dead-letter queue for failed messages

  • Register as Service Endpoint in PRT

Delegated vs Application Permissions

Delegated Permissions
  • Act on behalf of a signed-in user
  • User must be logged in at the time
  • Limited to what that user has access to
  • Used in: interactive flows, canvas apps calling Graph
  • OAuth flow: Authorization Code
  • User consent or admin consent required
Application Permissions
  • Application acts as itself — no user context
  • Works without any user logged in

  • Used in: scheduled flows, background jobs, plugins

🎯 EXAM — Scheduled Flows Need Application Permissions If a flow runs on a schedule (midnight sync, hourly report) with no user logged in and needs to call the Graph API, it MUST use Application permissions with the Client Credentials flow. Application Lifecycle Management, solution architecture, PAC CLI, and CI/CD pipelines

ALM (Application Lifecycle Management) is how professional Power Platform developers move work from development to production reliably, repeatably, and safely. It's 10–15% of the PL-400 exam and is the area most candidates underestimate.

Solution Architecture

A Solution is a container that packages Power Platform customizations (tables, forms, plugins, flows, apps, security roles, etc.) for transport between environments. Understanding solution types is foundational.

Solution TypeDescriptionWhere Used
UnmanagedSource solution — components visible and editableDevelopment environment ONLY
ManagedDeployment package — components locked; governed by publisher propertiesTest, UAT, and Production
PatchSubset of parent solution containing only changes since last versionQuick hotfixes between major releases
CloneFull copy of parent managed solution used to start the next major versionStarting a new major release
⚠️ NEVER Modify Managed Solutions in Non-DEV Environments Managed solutions in Test/UAT/Production lock their components. Any "customizations" made outside the solution in those environments create untracked technical debt that breaks upgrade paths and creates "solution layering" nightmares. All changes must flow from DEV (unmanaged) → export as managed → import to Test/Prod.

Security Flow in Plain English

User Request → Azure AD authenticates the user (right tenant, licensed?) → Security Role check (does this role have the required privilege on this table?) → Business Unit depth check (does the user's depth allow accessing this specific record's owner?) → Field Security Profile (are any columns on this record restricted for this user?) → Data returned.

PCF Lifecycle Order

init() (once, on control load) → updateView() (on every context or data change) → getOutputs() (called by platform after notifyOutputChanged()) → destroy() (on control unload). Never call notifyOutputChanged() from inside updateView() — infinite loop.

Custom Connector Auth Decision Tree

Modern API with user login? → OAuth 2.0 | Simple key in header or query string? → API Key | No credentials needed? → No Authentication | On-premises legacy system? → Windows Authentication + On-premises Data Gateway

ALM: Managed vs Unmanaged by Environment

DEV = Unmanaged | Test = Managed | UAT = Managed | Production = Managed. Export from DEV as unmanaged, unpack to XML, commit. Pack to managed, import to non-DEV. Simple rule: if it's not DEV, it gets managed.

IsBlank vs IsEmpty

IsBlank(text) → TRUE if the value is null or empty string. Use for: checking if a field has no value.
IsEmpty(table) → TRUE if the table/collection has zero records. Use for: checking if a query returned nothing. Never use IsEmpty on a text value — it returns FALSE for "".

Practice Exam

30 Practice Questions

Exam-style difficulty. No looking at chapters. Suggested time: 75 minutes.

Section 1 — Architecture & Dataverse (Q1–Q10)

P1: A company needs an app for field technicians to complete inspection checklists on mobile devices while offline in areas with no connectivity, syncing when connectivity returns. Data requires role-based access. Best approach?
B. Model-driven apps natively support offline profiles with Dataverse. Canvas apps have no native offline sync. Power Pages is for external web portals, not mobile offline scenarios.

P2: An Account table needs a column showing total revenue from all related active Opportunities, updating automatically. Which column type is correct?
B. Rollup columns aggregate across related records. Formula columns compute from the same record's columns only. JavaScript is client-side and doesn't persist the value. Calculated columns don't span tables.

P3: Projects and Employees have a many-to-many relationship. Each assignment needs to store Role (PM, Dev, Tester) and Start Date. How to model this?
B. Native N:N creates a system-managed intersect table with no custom columns. To store attributes ON the relationship itself, you need a manual junction table with two lookup columns plus your additional columns.

P4: A plugin on Account Create at Stage 20 (Synchronous) throws an unhandled NullReferenceException. What does the user experience?
C. Stage 20 runs within the DB transaction. Any unhandled exception rolls back the entire operation. The user sees the error message. Plugins do not auto-retry — that is a feature of async flows, not sync plugins.

P5: A plugin on Account Update reads a field via Target.Contains("industrycode") and it randomly returns false even though the field has a value. Root cause?
B. On Update, Target is not the full record — it's only the fields being changed in this specific update operation. Register a Pre-Image in PRT to get the full record state before the update.

P6: Which statement correctly describes Field Security Profiles?
C. Field Security Profiles operate at the column level. The column must first be set to "Field Security Enabled." Then a profile grants column-level permissions to assigned users/teams. System Administrators bypass FSPs — this is a common exam detail.

P7: A plugin fires on every Account update but only needs to fire when "Revenue" or "Industry" changes. Most efficient fix?
B. Filtering Attributes prevents the platform from invoking the plugin at all unless those specific fields are in the update. Option A reduces work inside the plugin but still invokes it on every update — less efficient.

P8: A Virtual Table shows data from an external REST API. Can you create a 1:N relationship from this Virtual Table to a standard Dataverse table using a Lookup column?
B. Virtual Tables represent external data without storing rows in Dataverse. Since there are no physical rows in Dataverse, traditional FK relationships with referential integrity cannot be enforced. This is a fundamental limitation of Virtual Tables.

P9: A Business Rule on the Opportunity table is scoped to "Entity." It sets Probability = 80 when SalesStage = "Proposal." A developer imports 500 Opportunities via the Web API with SalesStage="Proposal" and Probability=50. What happens?
B. Entity-scoped Business Rules run as a synchronous workflow on the Dataverse server and enforce on ALL writes — API, import, plugin, and form saves. Form-scoped rules only run in the browser. This is a key PL-400 differentiator.

P10: How do you cancel a form save from a JavaScript OnSave handler?
C. preventDefault() on the event args is the only supported way to cancel a save. Returning false does nothing. Throwing an exception shows an unhelpful technical error. setFormNotification shows a banner but does not stop the save.

Section 2 — Power Apps & Automate (Q11–Q20)

P11: A canvas app gallery connected to Dataverse shows 500 records instead of the 8,000 active accounts matching the filter. Cause?
B. The delegation limit defaults to 500 (max 2,000). If any part of the filter isn't delegable, Power Apps downloads only 500 records and filters them locally — returning incomplete results. Delegation warnings in Power Apps Studio flag this risk.

P12: In Power Automate, which expression correctly checks if an array variable "Emails" contains "admin@contoso.com"?
B. contains() works for both arrays (checks membership) and strings (checks substring). equals() compares the entire array to a string — wrong. indexOf() returns position, not boolean. includes() is JavaScript syntax, not a Power Automate expression function.

P13: After a PCF control calls notifyOutputChanged(), when does the platform call getOutputs()?
B. notifyOutputChanged() signals to the platform that new values are ready. The platform then calls getOutputs() at its own time to retrieve them. This is asynchronous. Never modify the value between notifyOutputChanged() and getOutputs().

P14: A Power Automate "Apply to each" loop processing 500 items is very slow. Which single change most directly reduces execution time?
A. By default, Apply to each runs serially — one item at a time. Enabling concurrency (Settings → Concurrency Control) runs multiple iterations in parallel, dramatically reducing total time for independent operations. Max concurrency is 50.

P15: Which Power Fx expression updates multiple existing records in a Dataverse table from a canvas app?
B. Dataverse doesn't support UpdateIf (that's for local collections). PatchAll doesn't exist. For bulk Dataverse updates from canvas apps, use ForAll with Patch for each record. Collect adds new records — doesn't update.

P16: A model-driven app tab should be hidden until Account Category = "Premium." Recommended no-code approach?
B. Business Rules support showing/hiding tabs, sections, and fields — no code required. For this simple conditional visibility based on a field value, a Business Rule is the recommended, maintainable, no-code solution. JavaScript would also work but adds complexity.

P17: Format a UTC date as "dd/MM/yyyy" in India Standard Time in Power Automate. Which expression is correct?
B. convertFromUtc() converts the timezone, then formatDateTime() formats it. Format string: dd=day digits, MM=month (capital M! mm=minutes), yyyy=4-digit year. Option A uses invalid uppercase tokens. Option C uses a non-existent function. convertTimeZone() is an Azure Logic Apps function, not Power Automate.

P18: A canvas app user reports IsEmpty(TextInput1.Text) returns false even when the text box is empty. Why?
B. IsEmpty() is for tables/collections — it checks if a table has zero rows. It returns false for an empty string "". To check if a text value is null or empty, use IsBlank().

P19: Power Automate custom connector uses OAuth 2.0. Users are repeatedly prompted to log in even after previously authorizing. Most likely cause?
C. Power Platform caches OAuth connections. Repeated login prompts indicate refresh token failure — either the offline_access scope is missing from the OAuth configuration, or the refresh token is expiring. Check the OAuth app registration for proper token lifetime and scope settings.

P20: A plugin needs to make an HTTP call to an external API to validate data synchronously before allowing a record to be created. The API takes up to 8 seconds. What is the correct plugin registration?
B. To cancel (prevent) a record creation based on validation logic, the plugin MUST run synchronously and before the DB write — Stage 20 (Pre-Operation). Stage 40 Async runs after the record is created, so cannot cancel it. Plugins can absolutely make HTTP calls (outbound HTTP is allowed in non-isolated plugins).

Section 3 — Integration, ALM & Advanced (Q21–Q30)

P21: A Webhook is registered to call an Azure Function when a new Account is created. The Azure Function is down for 2 hours. What happens to events during this time?
B. Webhooks are fire-and-forget HTTP POSTs with limited retries. No persistent queue. If the endpoint is unavailable beyond the retry window, the messages are lost. For guaranteed delivery, use Azure Service Bus (Service Endpoint in PRT).

P22: How do you set a lookup column (parentcustomerid) on a Contact to point to a specific Account using the Dataverse Web API?
A. To set a lookup (N:1) column via Web API, PATCH the entity with the @odata.bind annotation on the navigation property. The $ref approach (option B) is for N:N relationships. PUT replaces the entire entity record — dangerous and not recommended.

P23: CI/CD for Power Platform. Developers commit solution XML to GitHub (from unpacked solution). When code merges to main, it should automatically deploy to Test. Correct GitHub Actions approach?
B. The CD pipeline packs the XML source into a managed solution zip and imports it to Test. Non-DEV environments always receive managed solutions. The Configuration Migration Tool is for reference data, not customizations.

P24: A scheduled flow running nightly (no user logged in) needs to call Microsoft Graph to read emails across all mailboxes in the organization. Which permission type?
B. Scheduled flows run without a user session. Delegated permissions require an interactive user. Application permissions with Client Credentials (client_id + client_secret or certificate) allow the app to authenticate as itself and access all mailboxes. Admin consent is always mandatory for application permissions.

P25: Canvas app updates a Dataverse Account. Error: "You do not have permission to perform this action." The user's security role has User-level Write on Account. The account being updated is owned by another user. Cause?
B. Security role depth applies to BOTH read and write. User-level Write = can only update records you own. Business Unit Write = can update records owned by anyone in your BU. Organization Write = can update any record. This is the depth concept applied to update scenarios.

P26: A plugin references the Newtonsoft.Json NuGet package. When imported to Test environment, plugin fails with "Could not load file or assembly." Fix?
B. Dataverse plugins run in a sandbox — you cannot install software on the server. All dependencies must be merged into a single DLL using ILMerge or ILRepack before registration. Newer SDK versions also support registering dependent assemblies separately in PRT, but ILMerge is the classic exam answer.

P27: You need to send a Teams channel message every time a High Priority Case is created in Dataverse. Most maintainable Power Platform solution?
C. Power Automate with Dataverse trigger + Teams connector is the right tool — no code, maintainable, version-controllable in a solution. JavaScript fires on form open, not on record creation. Plugins can call external APIs but are more complex. This is the "right tool for the job" scenario.

P28: Which PAC CLI command packs a solution from source XML files as a managed solution for deployment to Test?
B. pac solution pack with --packagetype Managed produces a managed solution zip. Without --packagetype, it defaults to Unmanaged. Always specify Managed for non-DEV deployment. pac solution build is not a valid PAC CLI command.

P29: A custom connector POST action returns a JSON response with a nested array. In the flow, dynamic content from this action isn't available. Best fix?
A. Define the response schema with nested array details directly in the custom connector. This makes the connector self-documenting and enables Power Automate to generate dynamic content automatically. Option B (Parse JSON) is a workaround that works but requires schema definition anyway — the proper fix is in the connector definition itself.

P30: A developer is fixing a bug found in the Test environment. The bug is in a plugin step registered in a managed solution. The developer directly edits the plugin step in the Test environment. What is the problem with this approach?
B. Changes made directly in Test to managed components exist as an "active layer" that is overwritten the next time the managed solution is imported. The correct approach: fix in DEV (unmanaged), export managed, import to Test. Direct edits to managed solutions in non-DEV environments are technical debt that breaks ALM.
